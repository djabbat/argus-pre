Describe your project in a sentence ≤100 words A single-binary, local-first AI agent core written in Rust: it runs the full agent loop — decide, run, compress, repeat — and keeps every piece of state sessions, memory, tasks, skills in plain files on the user's own machine, working with any OpenAI-compatible local model Ollama, LM Studio, llama.cpp or a cloud API. MIT-licensed, no runtime beyond the binary itself, built for researchers, clinics and public institutions that cannot send sensitive data to cloud agents. 2. Describe your project more in-depth. Why is it critical? ≤300 words Agent platforms increasingly capture users' prompts, files, sessions and secrets in the cloud. I built the first version of this core because I could not send my own research data to a third-party server, and I could not find a local agent that was ready to use. For a growing number of users — clinical researchers, biomedical labs, hospitals, public institutions — that is simply not acceptable: patient-derived data, unpublished results and research notebooks cannot be sent to third-party servers, and dependence on closed, per-seat API billing is a real cost and governance burden. ARGUS-OS1 is a counter-path that works today: a complete agent core in one Rust binary that keeps every byte of state on the local disk, runs on consumer hardware with open-weight models, and costs nothing per inference. The project is critical for three reasons. First, sovereignty: it shows that a capable, tool-using agent can exist without a cloud backend, and that its whole operation is inspectable — plain-JSON state, audit trails, Obsidian and vector exports. Second, access: a zero-API-fee agent is usable by labs and students with no budget for token metering. Third, security surface: because the core is a single auditable binary with few dependencies, approval gates, SSRF guards and a shell sandbox, it offers a smaller and more reviewable attack surface than the large cloud SDKs it replaces. This is not a prototype. The core is at version 3.6 with 46 passing unit tests, a clean clippy run, a CI pipeline, reproducible GAIA-style benchmarks 80% on a 10-task multi-file set with a 7B local model and an installer. What is missing is exactly what this application funds: long-term maintenance, hardening, and the ecosystem work needed to turn a young but working component into widely reused base infrastructure. 3. Overview of your project's own, most important, dependencies ≤300 words The core deliberately keeps dependencies small so the binary is auditable and buildable offline. Runtime dependencies Cargo.toml : serde / serde_json plain-JSON state serialization , rand task scheduling , chrono timestamps , dirs state-directory resolution , reqwest with rustls-tls blocking HTTP for the web tool and LLM API calls , tungstenite + base64 WebSocket transport for the Chrome CDP bridge . There is no Node runtime, no interpreter and no cloud SDK. External runtime peers — not linked, optional, user-provided: any OpenAI-compatible LLM server Ollama, LM Studio, llama.cpp reached over localhost HTTP, and a Chrome/Chromium instance for the CDP browser tools. Both are optional; the agent runs with a local model and nothing else. This minimal-dependency posture is a feature: fewer transitive packages mean a smaller supply-chain surface, easier audits and reproducible builds — priorities for a tool meant to handle sensitive data. Rust memory safety and the rustls TLS stack further narrow the attack surface. 6. Projects that depend on your technology ≤300 words Adoption is at an early stage, and we state this plainly. Describe a specific scenario for the use of your technology ≤300 words A clinical research lab runs ARGUS-OS1 on a closed workstation inside its network, with Ollama serving a 7B–30B open-weight model on a local GPU. No data leaves the machine. The researcher gives the agent a plain-language goal: "Track the centriole-pedigree metrics in today's batch and draft the summary." The agent reads local microscopy annotations, computes the five pedigree metrics from the on-disk dataset, writes the summary into the project's Obsidian vault, and files a timestamped transcript of everything it did. Because state is plain JSON and the shell and file-write tools are approval-gated and sandboxed, a reviewer can verify exactly what the agent touched, and a failed step is recoverable from the persisted session. The same machine schedules overnight analysis as durable tasks, keeps the researcher's memory typed notes, lessons, procedures across sessions, and — when needed — uses the browser tools for literature look-up without document contents ever leaving the host. If the network is unavailable, the agent still works. This is the setup I run in my own research work, on a workstation holding microscopy data that cannot leave the building. The scenario meets the target groups' needs directly: privacy by default, zero inference cost, auditability, offline operation, and no vendor lock-in. 9. How was the work made possible so far? What are the challenges you currently face in maintenance? ≤300 words Single-maintainer risk: all knowledge currently sits with one person; there is no onboarding path, no bus-factor protection, and the issue backlog is untriaged. Security surface: the core drives real tools — shell, browser, web — and must stay ahead of sandbox escapes, SSRF edge cases and dependency updates; this work is continuous and invisible, and it is currently unfunded. Dependency maintenance: keeping the small dependency set current and supply-chain-clean SBOM, pinning, automated updates is unglamorous and unfunded. Governance: there is no governance or contribution model, no SECURITY.md disclosure process, and no release cadence. Documentation: docs exist DOCS.md but there are no tutorials, translations or a contribution guide beyond CONTRIBUTING.md. Long-term planning: the roadmap is maintained but rests entirely on volunteer time; there is no funded capacity for reviews, mentoring or a second maintainer. 11. What are possible alternatives to your project, and how does it compare? ≤300 words Cloud agent platforms e.g., OpenAI and Anthropic agents are the mainstream alternative: capable, but closed-source, cloud-locked, per-token billed, and unusable where data cannot leave the premises. Open-source agent frameworks AutoGPT, LangChain/LangGraph, OpenHands are typically Python-heavy, pull large dependency trees, and default to cloud models and cloud-native storage. Research cores e.g., Atomic Agent demonstrate tool-use but are research artifacts without packaging or a maintenance model. Personal assistants such as pi are single-user tools, not embeddable components. ARGUS-OS1 differs on three axes. One binary: a compiled Rust core with minimal dependencies and no runtime to install. Local-first by design: sessions, memory, tasks and skills live in plain files; there is no cloud storage layer at all. Honest safety: approval-gated dangerous calls, SSRF guard with DNS resolution, shell sandbox, session-only escalation modes, loop guard. Its weak spot is adoption: the alternatives have communities and integrations, and ARGUS-OS1 does not yet. That is the gap this request is built to close — the requested activities are adoption, packaging, hardening and maintainership, not another feature race. 12.
